## Задача

Сделать службу поддержки:
- клиенты создают заявки и переписываются с поддержкой;
- сотрудники разбирают очередь, отвечают и следят за сроками;
- старший сотрудник распределяет заявки и видит общую картину.

```
apps/api         — NestJS
apps/web         — Next.js: кабинет клиента и рабочее место сотрудника
packages/shared  — Zod-схемы и типы
```

Монорепо на workspaces, один lock-файл в корне.

## 1. Данные

PostgreSQL, схема и миграции — Drizzle.

**Роли:**

- `customer` — видит только свои заявки;
- `agent` — работает с заявками своих категорий;
- `lead` — видит всё, назначает, настраивает сроки.

**Заявка:**

| Поле | Правила |
| --- | --- |
| номер | `HD-1042`, сквозной, без пропусков и повторов |
| `subject` | 1–200 символов |
| `category` | из справочника: оплата, доставка, аккаунт, техническая проблема, другое |
| `priority` | `low`, `normal`, `high`, `urgent`; клиент выбирает из первых трёх, `urgent` ставит только сотрудник |
| `status` | `new`, `open`, `pending` (ждём клиента), `resolved`, `closed` |
| `assignee` | сотрудник или никто |
| `tags` | список строк |
| сроки | срок первого ответа и срок решения — по SLA |

**Сообщения в заявке:**

- публичный ответ — видит клиент;
- внутренняя заметка — клиент её не видит ни в интерфейсе, ни в API;
- вложения до 10 МБ, до 5 на сообщение, только картинки, PDF и текст.

**История заявки:** кто, когда и что изменил — статус, приоритет, исполнителя, категорию.

**Сид:**

- 20 000 заявок за полгода во всех статусах;
- 200 клиентов, 6 сотрудников с разными категориями, 1 `lead`;
- логины и пароли — в README.

## 2. Правила

**Переходы статусов:**

- Сотрудник ответил публично на `new` или `pending` — `open`.
- Клиент ответил на `pending` или `resolved` — `open`.
- `resolved` без ответа клиента 3 дня — `closed`, фоновой задачей.
- `closed` не открывается снова: новый ответ клиента создаёт новую заявку со ссылкой на старую.
- Остальные переходы — в README, с таблицей.

**SLA:**

| Приоритет | Первый ответ | Решение |
| --- | --- | --- |
| `urgent` | 1 час | 4 часа |
| `high` | 4 часа | 1 рабочий день |
| `normal` | 1 рабочий день | 3 рабочих дня |
| `low` | 2 рабочих дня | 5 рабочих дней |

- Время считается в рабочих часах: пн–пт 9:00–18:00 по Киеву. Сроки задаёт `lead`.
- В `pending` таймер на паузе.
- Смена приоритета пересчитывает сроки от момента создания заявки.
- Фоновая задача отмечает нарушения и предупреждает исполнителя за 30 минут до срока.

## 3. API (NestJS)

| Метод и путь | Назначение |
| --- | --- |
| `POST /auth/login`, `POST /auth/logout`, `GET /me` | Сессия в PostgreSQL, cookie `httpOnly` |
| `GET /tickets`, `POST /tickets`, `GET /tickets/:id`, `PATCH /tickets/:id` | Заявки |
| `POST /tickets/:id/messages` | Ответ или внутренняя заметка |
| `POST /attachments`, `GET /attachments/:id` | Загрузка и скачивание вложений |
| `POST /tickets/take-next` | «Взять следующую» из очереди |
| `POST /tickets/bulk` | Массовое действие над выбранными заявками |
| `GET /canned-responses` и CRUD | Шаблоны ответов |
| `GET /notifications`, `POST /notifications/read` | Уведомления в приложении |
| `GET /events` | Поток событий (SSE): новые сообщения, изменения заявок, уведомления |
| `GET /stats` | Показатели для `lead` |

**Общие требования:**

- Валидация — Zod-схемами из `packages/shared`.
- Единый формат ошибок. На любой некорректный ввод — `4xx`, никогда `5xx`.
- Swagger на `/docs`.
- Права проверяются на сервере в каждом эндпоинте:
  - клиент не видит чужие заявки, внутренние заметки и чужие вложения;
  - `agent` не видит заявки чужих категорий, если они не назначены на него.

**Список заявок:**

- Фильтры: статус, приоритет, категория, исполнитель («мои», «без исполнителя»), нарушен SLA, теги, период.
- Полнотекстовый поиск по теме и сообщениям (PostgreSQL full-text).
- Сортировка по сроку SLA, дате создания или обновления.
- Курсорная пагинация. Любой запрос по 20 000 заявок — быстрее 200 мс; индексы описаны в README.

**Конкурентность:**

- **«Взять следующую»** выдаёт самую срочную свободную заявку категорий сотрудника и назначает её на него. Шесть сотрудников нажали одновременно — шесть разных заявок.
- **Изменение заявки** идёт с версией. Если заявку уже изменил кто-то другой, — `409` с текущим состоянием, без молчаливой перезаписи.
- **Ответ** приходит с идентификатором, созданным на клиенте. Повтор (двойной клик, обрыв сети) не создаёт второе сообщение.
- **Номер заявки** не дублируется и не пропускается при одновременном создании.

**Массовые действия:** назначить, сменить статус, приоритет или теги — до 200 заявок за раз. Ответ по каждой заявке отдельно; заявки без прав или с недопустимым переходом пропускаются с причиной.

**Вложения:**

- Тип проверяется по содержимому файла, а не по расширению.
- Файл недоступен без прав на заявку.
- Вложения неотправленного сообщения удаляются фоновой задачей через сутки.

**Надёжность:**

- Фоновые задачи (SLA, автозакрытие, очистка) — на PostgreSQL. Перезапуск `api` ничего не теряет и ничего не делает дважды.
- Завершение по `SIGTERM`: текущие запросы дорабатывают, выход с кодом `0`.
- Проверки состояния: `GET /health` и `GET /ready`.
- Вход ограничен по числу неудачных попыток.

## 4. Кабинет клиента (web)

- **Создание заявки:** тема, категория, приоритет, описание, вложения. Черновик сохраняется и переживает перезагрузку.
- **Мои заявки:** список со статусами; непрочитанные ответы выделены.
- **Заявка:**
  - переписка без внутренних заметок;
  - ответ с вложениями;
  - новые ответы поддержки появляются без перезагрузки;
  - «Проблема решена» и оценка после решения: 1–5 и комментарий.

## 5. Рабочее место сотрудника (web)

**Очередь:**

- Таблица заявок с фильтрами и поиском. Фильтры хранятся в URL; «Назад» работает.
- Сохранённые представления: «Мои открытые», «Без исполнителя», «Горит SLA» и свои.
- Время до нарушения SLA обновляется на экране; просроченные выделены.
- Новые и изменённые заявки появляются без перезагрузки, не сбрасывая прокрутку и выделение.
- Выделение нескольких заявок и массовые действия с отчётом о пропущенных.
- Кнопка «Взять следующую».
- Горячие клавиши: `j`/`k` — по списку, `Enter` — открыть, `/` — поиск. Справка по `?`.

**Заявка:**

- Лента: сообщения, внутренние заметки и изменения полей — по времени. Заметки визуально отличаются от ответов.
- Боковая панель: статус, приоритет, категория, исполнитель, теги, SLA. При конфликте версий — сообщение и актуальные данные, введённое не теряется.
- **Редактор ответа:**
  - переключатель «ответ / заметка», и по ошибке не отправить заметку клиенту;
  - черновик на каждую заявку, переживает перезагрузку;
  - вставка шаблона с подстановкой имени клиента и номера заявки;
  - вложения перетаскиванием, с прогрессом загрузки и отменой;
  - `Ctrl/Cmd+Enter` — отправить;
  - отправка с выбором статуса: «отправить и ждать клиента», «отправить и решить».
- **Индикатор «Сейчас отвечает: Иван»**, если другой сотрудник пишет ответ в этой же заявке.

**Уведомления:** колокольчик со счётчиком — назначена заявка, клиент ответил, SLA скоро нарушится. Клик ведёт в заявку.

**Для `lead`:**

- Показатели за период:
  - заявок создано и решено;
  - среднее время первого ответа и решения;
  - процент нарушений SLA;
  - средняя оценка;
  - нагрузка по сотрудникам.
- Настройка сроков SLA.
- Шаблоны ответов.

## 6. Доступность и локализация

- **Доступность:**
  - формы с ошибками, связанными с полями;
  - весь путь клиента и сотрудника доступен с клавиатуры;
  - новые сообщения объявляются скринридером;
  - axe без нарушений.
- **Локали `uk` и `en`:**
  - даты и относительное время («через 2 години», «in 2 hours»);
  - склонения;
  - время всегда показано в часовом поясе пользователя.
- Тёмная тема.

## 7. Инфраструктура

- `docker compose`: `postgres`, `api`, `web`. Миграции и сид — автоматически. Вложения — в volume.
- Единственный ручной шаг — `cp .env.example .env`.
- Multi-stage Dockerfile, непривилегированный пользователь.
- CI (GitHub Actions): lint, typecheck, тесты, e2e. Последний коммит — зелёный.

## 8. Тесты

- **api (на настоящем PostgreSQL):**
  - права: клиент, `agent` чужой категории, внутренние заметки, вложения;
  - переходы статусов;
  - SLA: рабочие часы, выходные, пауза в `pending`, смена приоритета;
  - «Взять следующую» при одновременных запросах;
  - `409` при одновременном изменении;
  - повтор ответа с тем же идентификатором;
  - номера заявок при одновременном создании;
  - автозакрытие и очистка вложений;
  - некорректный ввод — `4xx`.
- **web — юнит:**
  - формы и их ошибки;
  - черновики;
  - наложение событий SSE на список;
  - горячие клавиши.
- **e2e (Playwright):**
  - клиент создаёт заявку с вложением, сотрудник отвечает, клиент видит ответ без перезагрузки;
  - внутренняя заметка не видна клиенту;
  - два сотрудника меняют одну заявку — второй получает конфликт;
  - массовое действие с пропусками;
  - фильтры, URL, «Назад».
